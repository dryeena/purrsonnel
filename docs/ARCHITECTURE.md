# Architecture

## Boundaries

One repository, one API process, one PostgreSQL database, one browser app. PostgreSQL stores the notification outbox; there is no Redis, search cluster, or separate worker service. Development Compose serves Vite; release-style Compose serves compiled static assets through nginx and routes same-origin API requests to Rust.

`apps/api/src/app.rs` owns route composition. `auth/` resolves opaque cookie sessions to a `Principal`; future providers must use this same principal. `features/` contains people, organization, terms, volunteers, hiring, lists, dashboard, and configuration. Features own validation, permissions, workflow transactions, and audit calls. Entities model persistence and relations; repositories own SeaORM/SeaQuery operations and isolated PostgreSQL projections and concurrency statements. No SQL strings live in auth or feature workflows. See SEAORM.md.

`AppState` contains a SeaORM database connection/pool, validated immutable configuration, and a bounded process-local mutation limiter. No privileged runtime configuration comes from the browser. Errors return a safe `{type,title,status,detail}` envelope. Logs omit query strings, QR tokens, cookie values, note bodies, and application responses.

## Authorization

The database `has_permission(actor, permission, department)` function resolves global, department, and division grants. `visible_person` resolves active memberships; the same person may be visible in multiple departments. Frontend hints only improve navigation. API checks and filtered queries make the access decision. Personnel rank and volunteer eligibility never confer permissions.

People reads intentionally omit email and legal name unless separately permitted. Application list responses omit all answers; detail responses remove sensitive answers for readers without the sensitive permission. Note visibility is evaluated separately from general HR management. Audit data excludes sensitive free text.

## State and consistency

Mutations with multiple effects run in SQL transactions. Final hiring locks the application and posting/level, records one immutable decision, upserts membership, updates the personnel level without demoting a higher level, updates application status, writes audit and notification records, then commits. It never grants permissions or creates a session. Existing `pending_identity` records stay pending.

QR references are 256-bit random tokens. Only their SHA-256 hashes are stored. Entry locks serialize issuance, rotation, withdrawal, and decisions. Decision requests revalidate status, expiry, staff scope, and the self-approval rule; idempotency keys are tied to actor, entry, token hash, decision, and note, so a reopened entry cannot accidentally replay an earlier decision as a new approval. Preview GETs do not mutate data. The separate staff shortcut is only a URL generated by the browser.

Terms versions are immutable after publication, except for supersession metadata. Signing locks the term against concurrent publication and snapshots document hash, authenticated user, typed name, fixed affirmation, and server timestamps. Database triggers prevent changes to evidence and decision events.

Manager graph edits use a transaction advisory lock and a recursive cycle check. Membership histories end and new histories are inserted. Verified service years have a composite uniqueness constraint and are counted explicitly.

Bulk execution locks a reviewed job and each target, rechecks permission and `updated_at`, skips conflicts, audits every changed person, and persists outcomes. Execution is bounded to 250 targets. Supported operations are status and volunteer eligibility. Filters are a bounded, whitelisted AST, evaluated against up to 1,000 scoped directory records; runs reject larger populations rather than silently truncating. Add parameterized SQL compilation before expanding that bound.

## Frontend

`lib/api.ts` owns fetch, CSRF state kept only in memory, safe exports, and data hooks. Stale hook requests cannot update a new query. Successful mutations publish a refresh event. Local Preact state keeps dependencies small; no compatibility shim for React or global data library is necessary yet. Routing uses Preact Router, all API URLs are relative, and Vite owns the development proxy.

Components provide native form semantics, labeled controls, dialogs with focus trapping and restoration, explicit error messages, status text, empty/loading states, and mobile navigation. Feature components request actual API records; there is no browser-side mock data store or fake mutation-success handler. Runtime DTOs are currently TypeScript records with explicit auth types; introduce generated client schemas as the API stabilizes.

## Extension points

- Provider adapter: `auth/providers.rs`, with OIDC checks documented separately.
- New capabilities: whitelist in configuration, policy grants, backend check, optional UI navigation hint, integration tests.
- New profile/form field types: extend controlled server validation and generic frontend fields together.
- New bulk operations: validation allowlist, preview, transactional executor, snapshot-conflict tests; never reuse this channel for permission grants.
- Additional notification delivery: retain in-app records; add a transport only with a real provider contract.
- Private uploads: no upload endpoint is present yet; introduce a private storage trait and authorization before accepting files.

## Requests and installed app

`features/requests.rs` owns request validation, authorization, audience snapshots, and locked state transitions. `features/push.rs` provides the Web Push transport and durable PostgreSQL outbox worker. The worker runs inside the existing API process, leases at most four jobs concurrently, and never substitutes a queued/accepted message for a device-read receipt. API state may omit the push service, keeping requests/in-app notifications functional without credentials.

`alert_preferences.rs` owns account-scoped phone policy, with PostgreSQL timezone evaluation shared by enqueue and dispatch. `request_follow_up.rs` owns transactional notification creation, explicit sender schedules, immutable participant history, and a separate push-independent scheduler. Both interactive actions and scheduler lock the request first. Escalation checks authority at configuration and execution and adds only its explicit recipient. Outbox leases have unique tokens so an expired worker cannot overwrite the result of a newer lease. Suppressed jobs are retained as evidence without replaying them after opt-in. See REQUEST_FOLLOW_THROUGH.md.

The web manifest and public service worker are dependency-free source files. The worker caches only public fallback assets, shows generic push notifications, and sends safe navigation messages to the app. Preact modules separate installation, device permission/subscription, connectivity/update notices, and dirty-form tracking from business features. Home-screen installation is a progressive enhancement; permissions and sessions still come from the same Rust middleware. See HOME_SCREEN_AND_REQUESTS.md for operational limits and the real-device acceptance path.
